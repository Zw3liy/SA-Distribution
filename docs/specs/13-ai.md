# Technical Specification — AI Domain

See [00-index.md](00-index.md) for cross-domain conventions.

## 1. Responsibilities

The AI Customer Assistant, product recommendations, AI search, and the future AI Operations/Developer Assistant modules from the standing project instructions. Owns the provider-agnostic AI service abstraction and every AI-touching feature — as a **read-only, pluggable consumer** of Catalog/Orders/CRM/Analytics data, per the Phase 4 dependency diagram's explicit "no solid arrows" rule for this domain.

## 2. Business Rules

- No other domain ever calls into AI synchronously as a required step of its own core logic — checkout, order fulfillment, and every other transactional flow must succeed identically whether the AI domain is fully operational, degraded, or entirely disabled. This is the direct, load-bearing consequence of Phase 4 §3's instruction that AI must be "first-class... but pluggable, not load-bearing," and it is treated as a hard architectural constraint, not a preference.
- AI provider access (whichever LLM/embedding vendor is used) sits behind a single internal interface (`AiProviderInterface`) — no domain-facing code anywhere references a specific vendor SDK directly, so the underlying provider can change without touching consumers.
- Recommendation and search results are always a **ranked suggestion**, never an authoritative data source — e.g., an AI-suggested "related product" still resolves through Catalog's real `ProductRepository` before being shown, so a hallucinated or stale suggestion can never surface a product that doesn't actually exist or isn't actually active/sellable.
- Conversation logs (`AiConversation`) are retained for quality/debugging purposes but are treated as containing potentially sensitive customer input — subject to the same data-handling care as any other customer PII, not a special "it's just AI logs" exemption.

## 3. Database Tables

| Table | Status | Notes |
|---|---|---|
| `ai_conversations` | new | `id, user_id NULL, channel, started_at` |
| `ai_messages` | new | `id, conversation_id, role ENUM('user','assistant','system'), content, created_at` |
| `ai_recommendation_feedback` | new | `id, product_id, recommended_for_product_id, shown_at, was_clicked` — feeds future recommendation-quality tuning |

## 4. Entity Definitions

`AiConversation`, `AiMessage`, `AiRecommendationFeedback` — all new. No embedding/vector store table is defined at the relational-schema level in this phase — vector search, if adopted, uses a purpose-built store (not shoehorned into MariaDB), decided when AI search is actually implemented (§19/§20).

## 5. Service Interfaces

```
interface AiProviderInterface { // the one vendor-facing boundary in the whole platform
    public function complete(string $prompt, array $context): string;
    public function embed(string $text): array; // vector, for future search use
}
interface RecommendationServiceInterface {
    public function relatedTo(int $productId, int $limit): array; // returns real Product entities, via Catalog's service — never raw AI output
}
interface AssistantServiceInterface {
    public function respond(int $conversationId, string $userMessage): string;
}
```

## 6. Repository Interfaces

`AiConversationRepositoryInterface`, `AiMessageRepositoryInterface`, `AiRecommendationFeedbackRepositoryInterface` — standard CRUD/append shape.

## 7. Controller Responsibilities

`AssistantController` (customer-facing chat widget endpoint — session-scoped conversation), `AdminAiConfigController` (provider settings, feature-flag-gated rollout, staff-only).

## 8. Validation Rules

User messages to the assistant are length-capped and sanitized before being sent to `AiProviderInterface::complete()` (basic input hygiene, not a substitute for the provider's own safety systems). `RecommendationServiceInterface::relatedTo()` always filters its candidate set through Catalog's real active/sellable check before returning — enforced in code, not left as an assumption about what the AI provider returns.

## 9. Events Published

`Ai\Events\ConversationStarted`, `RecommendationShown`/`RecommendationClicked` (feeds Analytics and the feedback table in §3 for future tuning).

## 10. Events Consumed

`Catalog\Events\ProductCreated`/`ProductUpdated` (keeps a search/recommendation index fresh, if/when one is built — see §19 for what's actually in scope this phase), `Analytics`-published aggregates where useful for grounding recommendations in real behavioral data rather than product metadata alone.

## 11. Permissions Required

`ai.config.manage` (staff — provider settings, feature-flag control). The customer-facing assistant requires no permission, only whatever Identity/session state the assistant needs to personalize a response (and functions for anonymous/guest sessions too, degraded to non-personalized behavior).

## 12. API Endpoints

No public partner-facing API in this phase — the assistant is a first-party, storefront-embedded feature, not an externally-exposed capability yet.

## 13. UI Pages

A storefront-embedded assistant widget (not a standalone page — mounted into the existing page shell via `components/`), product-detail "related products via AI" section (visually indistinguishable from Catalog's existing rule-based related-products, per §2's ranked-suggestion rule — it's an enhancement to an existing surface, not a new page). `/admin/ai/settings` — staff-only.

## 14. Error Handling

`AiProviderUnavailableException` — caught at every call site and degraded gracefully (assistant shows a "temporarily unavailable" state; recommendations silently fall back to Catalog's existing non-AI related-products logic, which already exists and already works — this is not hypothetical, it's the exact Phase 3 `getRelatedProducts()` method). No AI failure is ever allowed to surface as a generic 500 error on a storefront page.

## 15. Logging Requirements

Every `AiProviderInterface` call is logged with latency and success/failure (operational health signal, since this is the platform's one true external-vendor dependency in this domain). Conversation content itself is stored in `ai_messages` (§3), not duplicated into the general application log, to keep sensitive content out of less-access-controlled log files.

## 16. Security Requirements

`AiProviderInterface` implementation holds the vendor API key/credentials — sourced from Administration's `SystemSetting` (encrypted at rest if the settings-storage mechanism supports it; flagged as a requirement on `SystemSetting`'s implementation, not just this domain's) or environment configuration, never hardcoded. Conversation logs containing customer PII are subject to the same access-control and retention consideration as any other customer data store (Customers domain's data-handling posture, referenced here rather than reinvented).

## 17. Performance Requirements

`AiProviderInterface::complete()` calls are expected to be the slowest operation anywhere in the platform (typical LLM latency) — every caller must treat it as such: timeouts, no blocking of unrelated page rendering, and (per §2) never on any transactional critical path where a slow or failed call would delay checkout or fulfillment.

## 18. Testing Strategy

Unit: `RecommendationService::relatedTo()` — the Catalog-filtering behavior specifically (a mocked AI provider returning a product ID that's since been deactivated must never appear in the result). Unit: graceful-degradation behavior of every consumer when `AiProviderInterface` throws. Integration: none against a real external AI provider in automated tests (non-deterministic, costs money, and not appropriate for a CI-style regression suite) — provider integration is verified manually/by a stubbed provider implementation instead.

## 19. Migration Strategy (Phase 5 implementation scope)

**In scope:** build `ai_conversations`, `ai_messages`, `ai_recommendation_feedback` tables; `AiProviderInterface` (with a real implementation behind a feature flag, per Administration's `FeatureFlagServiceInterface`, so it can ship dark and be enabled deliberately); `RecommendationService` wrapping Catalog's existing `getRelatedProducts()` with an AI-ranked ordering layered on top (existing method, not replaced — augmented, matching §2's "ranked suggestion, never authoritative" rule concretely); the assistant widget and its controller, feature-flag-gated off by default.

**Explicitly out of scope:** AI search (a real search index, vector or otherwise, is a larger infrastructure decision deferred until there's enough Catalog data volume to justify it over the existing SQL-based `search` filter); AI document processing, AI Operations/Developer Assistant (named in the standing project instructions' long-term AI strategy but not scoped into this implementation pass — no concrete requirement exists yet to build against).

## 20. Future Enhancements

AI-powered search (vector/embedding-based), AI document processing (supplier invoices, PO matching — ties into Suppliers/Finance), AI Operations Assistant (ties into Administration/Analytics), AI Developer Assistant, recommendation-quality tuning using the `ai_recommendation_feedback` data collected from day one of this domain's operation.
